# 16 工站 / 流程 / 工具配置重构评估

> **性质**：设计评估（对照用户提案与当前 `VisionPlatform` 实现），**不含代码变更**。  
> **方案口径**：[`通用视觉平台开发方案/docs/26-工站流程工具配置重构.md`](../../../通用视觉平台开发方案/docs/26-工站流程工具配置重构.md) —— 产品向结论、**架构图 / 类图**、细则收口以 26 为准；本文补代码映射与迁移阶段。  
> **关联文档**：`通用视觉平台开发方案/docs/05-方案与流程.md`、`06-工站-流程-工具说明.md`、`16-数据持久化.md`；本仓库 `docs/15-工具插件方案.md`、`docs/architecture.md`。

---

## 1. 用户提案摘要

1. **分层自持配置**：工站实例持 `StationConfig`，流程实例持 `JobConfig`，工具实例持工具侧配置（不再把多种语义混在一个扁平结构里）。
2. **连线以工具为真源**：流程需要连线时，从各工具实例读取；连线挂在工具上，而不是以 Job 级独立图为主。
3. **工具实例四块**：`ToolInfo`（身份）、`ToolLink`（输入连线）、`ToolPara`（配方参数，含界面 ROI / algLib / deviceId）、`ToolIO`（本拍综合运行数据，**不落盘**）。
4. **`AlgorToolBase`**：尚未定稿；可轻量参考既往「machine」类项目的算法工具模式。

下文先描述**现状**，再评估提案，给出**推荐形态**、**连线归属**、**持久化与运行态分界**、**AlgToolBase 开放问题**、**迁移阶段**与**风险**。

## 2. 当前实现概览（VisionPlatform）

### 2.1 领域层级与归属

| 层级 | 配置类型 | 存放位置 | 运行态 |
| --- | --- | --- | --- |
| 方案 | `Solution` | `*.vpsol` JSON 根 | `dirty`、路径等 |
| 工站 | `StationConfig` | `Solution.stations[]` | `Station` + 运行 tick（不进 JSON 的调度状态） |
| 流程 | `JobConfig` | `StationConfig.jobs[]` | `Job` + `JobRuntime` |
| 工具实例 | `ToolConfig` | `JobConfig.tools[]` | `Tool` + `ToolRuntime`；`ToolConfig.runtime` 字段**不落盘** |

**结论（相对提案 1）**：「每层实例拥有自己的 Config 类型」**已基本成立**。工站/流程/工具配置都嵌在方案 JSON 内，由 `VisionConfigMgr` 统一读写（见 `16-数据持久化.md`）。尚未完全对齐的是：**工具实例内部**仍把多种语义挤在单一 `ToolConfig` 里，且 Job 仍额外持有整图级 `links[]` 与 `root` 执行树。

### 2.2 `JobConfig` 的双结构（执行 vs 数据）

当前一条流程同时维护：

```text
JobConfig
├── tools[]          扁平工具实例列表（ToolConfig）
├── links[]          端口级数据连线（ToolLink），含画布路由拐点
├── root             ToolGroup 执行树（顺序 / 并行 / If）
├── resultRules[]    结果矩阵
└── trigger / failPolicy / …
```

- **执行顺序**：`Job::runGroup` 遍历 `root`（`toolExecOrder` 等辅助）。
- **数据流**：调度按 `links[]` 解析上游输出，填充 `ToolIn.inputIo`（见 `Job.cpp` 与 `ToolIo.h`）。
- **同步逻辑**：存在 `rebuildLinksFromTree` / `rebuildSerialLinks` / `ensureJobTree`——执行树与连线可相互推导或修补，是**常见痛点来源**（两处真源、合并冲突、画布操作与树编辑不同步）。

与产品文档 `06-工站-流程-工具说明.md` 描述一致：**执行结构**与**数据结构**刻意分离；Proposal 2 倾向于把数据结构从 Job 下沉到工具。

### 2.3 `ToolConfig` 字段（实例「配方 + 表现」混合）

当前 `ToolConfig`（`VisionCore/model/ToolConfig.h`）大致包含：

| 语义 | 字段 | 持久化 |
| --- | --- | --- |
| 身份 / 类型 | `id`, `toolName`, `type`, `name`, `enabled` | 是 → 目标态 `ToolInfo` |
| 算法与设备绑定 | `algLib`, `deviceId` | 是 → 目标态归入 `ToolPara`（非 Info） |
| 算法与调试参数 | `params` | 是 → `ToolPara` |
| 运行态参数副本 | `runtime` | **否**（加载时 `migrateToolRuntime` 会把误写入 params 的运行态键迁出） |
| ROI | `rois[]` | 是 → 目标态归入 `ToolPara`（界面绘制；非 IO） |
| 画布布局 | `canvasX/Y`, `canvasPlaced` | 是 |

Draft 编辑已部分抽象为 `ToolRecipe`（params + rois + deviceId），与 `StationRecipe` / `DeviceRecipe` 模式一致（`RecipeDraft.h`）。

**相对提案 3**：`ToolInfo` / `ToolPara` / 部分「IO 配置」已存在，但**未显式分类型**：**没有** per-tool 的 `ToolLink` 列表；结果图像与调试几何主要在**运行态**（`JobRuntime`、`ToolRuntime`、`ToolOut.io`），而非持久化 `ToolIO`。

### 2.4 插件 `ToolBase` vs 实例配置（命名冲突）

| 名称 | 含义 | 生命周期 |
| --- | --- | --- |
| `ToolBase`（`VisionToolBase`） | **工具类型插件**：端口表、缺省参数、`execute` | 进程内注册表 `ToolRegistry` |
| `ToolConfig` | **流程内工具实例**配方 | 方案 JSON |
| `Tool` | 实例运行时：指向 `ToolConfig` + `ToolRuntime` | `Job` 拥有 |
| `AlgorToolBase` | **图像算法后端**原型，按 `(toolName, algLib)` 注册 | `AlgorToolBaseRegistry` |

用户提案中的「ToolBase 含四结构」若字面套在插件类 `ToolBase` 上，会与现有插件架构冲突（插件无实例 id、无 ROI、无连线）。评估见 §4。

### 2.5 持久化与旁路数据

- **方案 JSON**：工站、`JobConfig`（含 `tools`、`links`、`root`、结果规则）、`runtimeView` 等（`VisionConfigMgr::jobToJson` / `toolToJson`）。
- **不落盘**：`JobRuntime`、`ToolRuntime`、`ToolConfig.runtime`、单次运行缓存图。
- **旁路目录**：`*.vpdata/<toolId>/` 存模板、模型等大文件（`SolutionDataPaths`）。

### 2.6 三层 IO 模型（已与提案部分一致）

`docs/15-工具插件方案.md` 与 `08-工具与算法工程.md` 已约定：

```text
VisionCore     连线、调度、ToolConfig 持久化
    ↓ ToolIn / ToolOut（含 ToolIo）
ToolBase 插件   execute；图像类再调 runAlgorToolBase
    ↓ AlgorToolIn / AlgorToolOut
AlgorToolBase   纯像素计算，不见方案/端口
```

这与用户希望的「Para / IO 分界」在**运行时**清晰，但**持久化**仍集中在 `ToolConfig.params` + `rois`，未单独建模 `ToolIO` 持久层。

## 3. 当前主要痛点

1. **Job 级 `links[]` 与 `root` 双真源**：画布拖线、自动串行重建、树结构调整可能互相覆盖；调试「谁为准」成本高。
2. **`ToolConfig` 语义过载**：身份、参数、ROI、画布坐标、运行态字段同 struct；UI / 序列化 / draft 对比都要特殊分支（如 enhance/smooth pipeline）。
3. **连线查询路径经 Job**：`ToolIoPanel`、`findLinkToPort` 等必须持有 `JobConfig*`，无法只凭工具实例完成「我的输入从哪来」。
4. **「IO」边界模糊**：持久 ROI vs 运行结果图叠加 vs 调试变量（`runtime` 键）分散在三处（`ToolConfig`、`JobRuntime`、`ToolOut`）。
5. **命名**：「ToolBase」在沟通中既指插件又指实例聚合，易与提案 3 混淆。
6. **Alg 层演进中**：插件化后 `AlgorToolBase` 已瘦身为 `(toolName, algLib) + run()`；与旧文档 `08` 中「VisionAlgoBase 大包」叙述部分过时，需单独定稿（见 §8）。

## 4. 提案对照与总体结论

| 提案点 | 与现状关系 | 评估 |
| --- | --- | --- |
| 1. 分层自持 Config | 已有 `StationConfig` / `JobConfig` / `ToolConfig` | **保留**；可加强「实例对象只通过 Config 访问配方」的命名与文件布局，无需推翻 Solution 根 |
| 2. 连线在工具上 | 现为 `JobConfig.links[]` | **方向正确**，建议采用「**工具存输入边 + Job 可缓存索引**」混合，而非完全取消 Job 级视图 |
| 3. 四结构 ToolInfo / Link / Para / IO | 部分落在 `ToolConfig` + 运行态 | **建议采纳为实例侧逻辑拆分**（新类型或嵌套 struct），**不要**并入插件 `ToolBase` 类 |
| 4. 参考 machine 项目 | 仓库内未找到独立工程或文档 | **无法对照**；以本仓库 `15-工具插件方案`、`AlgorToolBase.h` 为基准，machine 仅作外部经验可选 |

**总体 verdict（实施倾向）**：

- **推荐**：在 **VisionCore/model** 内重构 **工具实例记录** 的**逻辑分块**与**连线归属**，保持 `VisionConfigMgr` 单入口与 JSON 兼容策略。
- **不推荐**：把四块结构塞进 **插件** `ToolBase`；也不建议第一刀就删除 `ToolGroup` 执行树（并行/If 仍需要 Job 级结构）。
- **谨慎**：一次性把 `links` 从 Job JSON 根移到仅工具内存储，需版本号与双向迁移，否则旧方案无法打开。

## 5. 推荐数据形态（实例侧）

建议在现有 `ToolConfig` 内拆出嵌套四块语义（Info/Link/Para），运行门面 `Tool` 与 **Info/Link/Para/IO 四者平行**（**不另建 ToolRecord 包装类**；序列化仍可 flatten 到现有 JSON 键以兼容）。

### 5.1 `ToolInfo`（持久）

**只含身份**（产品口径与方案 26 一致；`algLib` / `deviceId` 归入 Para）：

```text
id, toolName, type, name, enabled
```

- 对应现有身份字段；`type` 仍以注册表 `ToolBase::type()` 为准做校验（与 `toolFromJson` 一致）。
- **不含**画布坐标（已定：流程布局表）。

### 5.1b 流程布局（已定：单独布局表）

产品口径（方案 26）：**单独做流程布局表**；工具不保存坐标/折线。ToolInfo 不含 canvas 字段。

### 5.2 `ToolLink`（持久，归属工具）

**推荐规则**：每条有向边描述「本工具某输入端口 ← 上游工具某输出端口」。

```text
struct ToolInputLink {
  PortSlot toPort;           // 本工具输入槽
  ObjectId fromToolId;
  PortSlot fromPort;
  // 不含 route/拐点 → 进 Job 布局表
};
```

- 工具侧：`std::vector<ToolInputLink> inputs;`（或 `incoming`）。
- **多输入 / 多类型端口**：一端口至多一条主连线（与现 `connectToolPorts` 替换语义一致）；若未来要多路合并，再扩展 `vector` 或显式 merge 工具。
- **Job 级 `links[]`**：Phase 2 起可作为 **派生缓存**（保存时 `links = flatten(tools[*].inputs)`），加载时若仅存在 Job.links 则 **回填** 到各工具。

**查询 API**：`Job` 调度时优先读工具内 `inputs`；`job.findLinkToPort(toId, port)` 改为扫描 tools 或读缓存。

### 5.3 `ToolPara`（持久）

```text
ParamMap params;   // 配方/算法/UI 调试参数
QString algLib;   // 算法后端，可换 → 参数而非身份
ObjectId deviceId; // 采集绑定设备，可换 → 参数而非身份
RoiList rois;      // 界面绘制的 ROI → 参数；不是 ToolIO
// pipeline 等仍可通过 params 或子对象 enhanceSteps 表达
```

- 运行态键 **禁止** 进入 `ToolPara`（延续 `migrateToolRuntime` / `isRuntimeParamKey`）。
- 与 `ToolRecipe` 对齐：draft 只 diff `ToolPara`（含 algLib / deviceId / rois）。

### 5.4 `ToolIO`（仅运行态，不持久化）

本拍综合后的运行数据（对齐现有 `ToolIo` / `ToolOut`，不另起第三套）：

| 内容 | 持久化 |
| --- | --- |
| 输入/输出图、结果图、区域、轮廓、位姿、逻辑量、debug、叠加 | **否**；留在 `ToolRuntime` / `JobRuntime` |

- **界面 ROI 不进 ToolIO**（已归 Para）。
- 不写入 `*.vpsol`；若需「上次调试截图」走 `vpdata` 或显式导出。
- 画布坐标属 **Job 流程布局表**，**不属** ToolInfo / ToolIO / ToolLink。
- ToolLink **只存两端**（fromTool/fromPort → toPort）；折线路由进布局表。

### 5.5 插件 `ToolBase` / `AlgorToolBase`（保持现状职责）

- **`ToolBase`**：类型元数据 + `execute(ToolIn)->ToolOut`。
- **`AlgorToolBase`**：仅 `run(AlgorToolIn)->AlgorToolOut`。
- 实例四块 **不进入** 上述插件基类。

## 6. 连线归属规则（推荐）

1. **权威存储（目标态）**：**输入边挂在消费方工具**（下游工具的 `inputs[]`）。理由：与 `ToolIn` / `ToolIoPanel`「为本端口选上游」交互一致；删除工具时清理其 `inputs` 及全 Job 内指向它的边即可。
2. **Job 仍保留**：
   - `root` **执行树**（并行/If/顺序）——**不可替代**；
   - `resultRules`、`trigger` 等流程级策略；
   - 可选 **`links[]` 冗余字段**（兼容旧文件、画布全局遍历加速），保存时由 tools 生成，加载时以 tools 为准；若两者冲突则定义优先级（建议 **tool.inputs 优先**）。
3. **树与线关系**：
   - 纯串行链：可继续提供「按树重建默认 image 连线」的**辅助命令**（现 `rebuildSerialLinks`），但用户手改连线后不得 silently 覆盖（需 UX 确认或仅改「未自定义」边）。
4. **跨 Job**：不允许；连线引用限定同一 `JobConfig.tools` 的 id。
5. **校验**：保存/加载时验证 `fromToolId`/`toToolId` 存在、端口类型匹配 `PortDesc`（可复用 `ToolRegistry` 端口表）。

## 7. 持久化 vs 运行态（明确分界）

| 数据 | 存储位置 | 说明 |
| --- | --- | --- |
| 工具身份、参数（含界面 ROI、algLib、deviceId）、输入连线、画布位置 | `*.vpsol` | 配方 |
| 工站 `runtimeView` | `*.vpsol` | 运行界面布局（非本机 settings） |
| 模板/模型文件 | `vpdata/<toolId>/` | 大资产 |
| `ToolConfig.runtime` / debug 键 | 内存；可从 params 迁移 | 禁止新写入 params |
| ToolIO（输出图、OK/NG、数值、耗时、本拍区域等） | `JobRuntime` / `ToolRuntime` | **不落盘** |
| 插件注册表 | 进程内存 | 非方案 |

**Draft 会话**（`ToolDebugHost`）：继续「正式配置 + 内存 draft」；Save 写回 formal 的 **ToolPara**（含 rois），不触碰 ToolIO 运行缓存。

## 8. `AlgorToolBase` 开放问题

当前实现（`VisionAlgToolBase/AlgorToolBase.h`）已插件化，与 `08-工具与算法工程.md` 早期「VisionAlgoBase 大包」叙述部分不一致。定稿前建议确认：

| 问题 | 现状 | 待定 |
| --- | --- | --- |
| 谁构造 `AlgorToolIn` | `runAlgorToolBase` 从 `ToolIn` 转换 | 是否在 Tool 插件内允许微调（如额外 region 源） |
| ROI 跟随位姿 | 在 `runAlgorToolBase` 内处理 | 是否暴露给 Para（如开关） |
| 多 ROI / 多 pose | `vector` 传入 | 与 `ToolIo` 多路输入的映射表 |
| `algLib` 选择 | `ToolConfig.algLib` + `getPreferred` | 缺库时错误语义（已：不注册 Builtin 占位） |
| 非图像工具 | 不实例化 `AlgorToolBase` | 无变化 |
| 线程安全 / 重入 | 文档要求可重入 | Halcon 句柄是否 per-run clone |
| machine 项目对照 | **本仓库未检索到** | 若用户本地有 SVN 其它路径，可补充：算法 DLL 边界、参数 JSON、是否与 Tool 壳合一 |

**轻量参考原则**（在不引入 machine 代码前提下）：

- 保持 **算法层不见 Job/连线**；
- 工具壳负责 **端口级 ToolIo → AlgorToolIn**；
- 实例 **Para** 只通过 `ToolIn.params` 下传。

## 10. 迁移阶段（建议）

### Phase 0 — 文档与命名（零行为变更）

- 统一术语：**实例配置** vs **类型插件 ToolBase**。
- 已与方案侧 [26](../../../通用视觉平台开发方案/docs/26-工站流程工具配置重构.md) 互链；后续再改 `05/06` 正文中「links 从 Job」表述。

### Phase 1 — 模型内聚（兼容 JSON）

- 在 `ToolConfig` 内引入嵌套四块（或 typedef 别名），字段布局与现 JSON **1:1 映射**。
- `VisionConfigMgr` 仍读写相同键；单元测试 round-trip。

### Phase 2 — 连线下沉

- 加载：若工具有 `inputs` 则用之；否则从 `Job.links` **拆分回填**。
- 保存：写 `inputs` + 可选写 flatten 的 `links`（format 版本 +1）。
- 改 `findLinkToPort`、`connectToolPorts`、`ToolIoPanel` 数据源。

### Phase 3 — 削弱双真源

- 执行树变更时，**不再默认**全量 `rebuildLinksFromTree`；改为提示或仅补「缺失 image 边」。
- 画布 `autoLayout` 仅动 layout 字段。

### Phase 4 — Alg 与 UI 对齐

- 按 `15-工具插件方案` 收束参数页生成；`AlgorToolBase` 定稿文档单独增补（或更新 `08` 第 3 节）。

### Phase 5 — 可选清理

- 新 format 稳定后停止写入冗余 `Job.links`；旧版只读兼容保留 2 个大版本。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| JSON format 分叉 | 旧方案打不开 | format 版本号；加载双路径；保存双写过渡期 |
| 连线回填错误 | 静默丢线 | 校验报告 + 打开方案时日志 |
| 并行/If 分支 image 边 | 树推导与用户线冲突 | 边标记 `auto` vs `manual` |
| Draft/正式不一致 | 调试保存丢连线 | draft 含完整 ToolLink 副本 |
| 性能（扫描 tools 找边） | 多 Job 调度变慢 | Job 级索引缓存于内存，保存时重建 |
| 丢 Halcon 资源路径 | algo 读 `toolDataDir` | 保持 `ToolIn` 注入，不写入 Alg 静态状态 |
| 提案 3 与插件 ToolBase 同名 | 重构范围失控 | 实例聚合禁止叫 `ToolBase`，用 `ToolInstance` / `ToolConfig` |
